## 一、本次 review 的最终结论

**保留现有 worker 体系和交付协议，把确定性流程从 Control 的语言理解中移出，变成可恢复、有界的自动推进；Control 只保留真正需要任务理解、且不能由既定规则决定的选择。**

与此同时，成本优化的重点应明确为：

> **减少昂贵 worker 的无必要调用、重复输入、重复读取，以及 Control 误判引起的重启和返工，而不是优先压缩廉价 Control 的 token。**

根据你对实际运行情况的反馈，worker 的行为和交付已经比较稳定。因此，下一版不应大幅重写 worker 协议，也不应把沙箱、权限代理或新的编排平台作为前置条件。最值得改造的是 **Control 与现有机械脚本之间的职责边界**。

## 三、明确自动化边界：有分支，不等于需要 Control

判断标准应当是：

> **只根据已验证状态、既有策略和来源记录，能否确定下一步？能，就由脚本执行；不能，再判断是否真的需要任务理解。**


| 场景                                          | 应由谁处理                          |
| ------------------------------------------- | ------------------------------ |
| 完成事件导入、去重、确认、必要的 one-shot 释放与清理             | 脚本                             |
| R0 后派 R1，满足既定条件时派 R2                        | 脚本                             |
| R1 明确返回 `fix_local`，对应 Owner 和 findings 已确定 | 脚本续接原 Owner                    |
| 来源已经明确要求承诺变更或返回 `plan_conflict`             | 脚本按规则转 Planner，不让 Control 重复分类 |
| 正常等待、可验证的同 session 恢复、明确失败后的合法重试            | 脚本                             |
| 新指令属于哪个 WP、是否改变既有范围，确实存在歧义                  | Control 理解任务并选择，必要时询问用户        |
| 多个合法方案涉及用户偏好、范围或业务优先级取舍                     | Control 在已有授权内选择               |
| 原生结果不明、状态不变量破坏、规则互相冲突                       | 机械核对；无法确认则停止，不交给 Control 猜测恢复  |


这里有两个重要限制。

**第一，Control 的“任务理解”不能扩大成领域解题。** 技术方案、证据真伪、结构性变更是否成立，仍应由 Owner、Reviewer、Planner 按职责判断。Control 可以组织问题、定位来源、选择路由，但不替它们编造结论。

**第二，脚本不能确定，不一定就是语义决策。** 缺少原生回执、两个规则同时匹配、事务状态损坏，首先是协议或工具问题，不应包装成“让模型选一个继续”。

## 四、目标形态：在现有体系上增加薄的自动推进层

建议沿用并扩展现有 `next_operation`，而不是另造一套编排系统。

目标流程是：

```text
原生事件 / 用户输入 / 已验证交付
                  ↓
     脚本校验状态、来源与允许动作
                  ↓
        自动完成确定性步骤
                  ↓
继续推进 / 等待 / 请求语义选择 / 有据停止
```

Orca 继续负责原生 task、session 和生命周期真相；现有 Guard、launcher、finalizer 继续承担原来的工作。新增层主要负责把这些能力**按规则连续调用，并在中断后恢复**。

### 建议的接口

下面是建议新增或统一的接口，不是当前已实现功能：

```text
mats advance
mats decide --decision-id <id> --choice <choice_id>
```

`advance` 自动推进当前允许的步骤，返回明确状态：


| 状态               | 含义                      |
| ---------------- | ----------------------- |
| `READY`          | 仍有确定性工作，本次因执行上限让出，可继续调用 |
| `WAIT`           | 正在等待 worker 或原生事件       |
| `NEEDS_DECISION` | 确实需要任务理解或授权范围内的语义选择     |
| `BLOCKED`        | 无法验证的原生结果、工具异常或协议问题     |
| `DONE`           | 当前授权范围内的任务已完成既定验收       |


**Control 可以多调用几次** `advance`**，但不应每次重新解释状态机。**

`NEEDS_DECISION` 应提供问题、来源、当前相关约束、合法选项及选项含义。Control 只返回选择和必要理由；packet、版本、哈希、session 身份、候选关联由脚本处理。

执行选择前，脚本必须重新验证相关对象版本。**旧决策不能作用于新 candidate、新契约或新的授权状态。** 这些依赖应由脚本保存，不要求 Control 搬运；也不宜因为一个无关 WP 更新就使全部决策失效。

## 五、Improvement Plan

### 阶段 A：先修事务正确性，同时建立最小成本归因

**目标：避免自动化把现有缺陷执行得更快、影响得更广。**

首先修复两个已有问题。

对 retry，应在可能覆盖交付内容之前完成适用的验证和操作预留，保留既有 attempt 的草稿。不能只移动写文件代码，还要处理“验证通过后、实际执行前状态发生变化”的情况。

对完成批次，应按 dispatch 持久化：

```text
imported
release_required
released
```

只有整批所需结果已导入、所有必要 one-shot 释放已确认、其他事件也处理完毕，才允许 acknowledge 和清理。**Owner 不进入 one-shot 清理。** 重放时依靠持久化处理记录，不能靠临时文件是否存在判断是否完成。

同时，由脚本为每次 worker 调用记录来源事件、角色、WP、原因码、启动/续接/恢复模式及返工原因。宿主能提供的 usage 再关联到这些记录；拿不到的费用或 token 标记未知，不让 worker 为监控多写报告。

**验收条件：** 两个新增回归测试通过；拒绝路径原草稿不变；多个 reviewer、Owner 与 reviewer 混合批次、释放失败和确认失败均不丢状态；重复事件不产生额外 worker 调用。

---

### 阶段 B：统一“下一步”与语义决策接口

**目标：Control 不再靠读协议和解释报错来完成确定性路由。**

以现有 [`routing.py`](http://routing.py)、Guard 条件和 workflow 为基线，将确定性转移集中到共享代码。下一步生成和动作准入应使用同一规则来源，避免出现：

```text
文档说一种流程
Guard 实现另一种限制
推进器又维护第三种理解
```

只将能机械判断的规则下沉。真正的语义选择继续保留决策指引和案例测试，不必先设计一个通用工作流语言。

随后，以稳定的 `reason_code`、结构化状态和动作标识替代精确错误文本路由。文本仍可解释原因，但不再是程序接口。

对 Planner、R2、新 Owner、重试和释放等昂贵或难恢复的动作，要求明确的来源与适用条件。**明确符合条件的动作自动执行；没有依据的动作，不能因为 Control 写了一句解释就获准执行。**

**验收条件：** 固定流程不要求 Control 解读错误字符串或拼接机械参数；重复或过期 action/decision 不重复生效；明确的 `fix_local`、review 升级、plan conflict 等按既定规则直接推进；只有实际歧义才生成决策请求。

---

### 阶段 C：实现有界自动推进和中断恢复

**目标：正常链路自动执行，故障恢复不再依赖 Control 临场设计。**

优先打通最常见的闭环：

```text
完成事件
→ 结果导入
→ R0
→ R1 / 必要 R2
→ 明确的局部修复回到同 Owner
→ 验收检查
→ Guard 证明 Owner 释放是剩余阻塞项后释放
→ 再次 guarded accept
→ 解锁下游
```

这里的 `advance` **不是一个跨所有原生调用的原子事务**，而是多个可恢复步骤的组合。

对有副作用的逻辑操作，保存脚本生成的 `operation_id`、相关对象版本和执行进度。区分“尚未执行”“原生结果不明”“原生成功已确认”“语义提交完成”“事件确认完成”。

**超时或没有看到输出，不等于失败。** 结果不明时先根据原生身份核对；无法安全确认就停止，而不是新建一个 worker 再做一次。不能在没有原生接口支持的情况下承诺跨系统 exactly-once。

自动化还应有步数、新 dispatch 数、重复修复和无进展上限。否则，原本由 Control 犹豫才打断的错误循环，可能变成连续消耗昂贵 worker 的自动循环。

操作日志只记录执行意图与回执，不复制另一份业务状态，也不替代 Orca 的生命周期权威。

**验收条件：** 在启动、binding 提交、导入、释放、确认和清理前后注入故障，系统能恢复或明确停止；不盲重试、不提前释放 Owner、不跳过 R2、不重复提交同一结果。缩短锁之前，必须先具备预留和过期操作隔离。

---

### 阶段 D：根据实际数据削减 worker I/O

**目标：让 worker 少读无必要内容，而不是仅让 packet 文件看起来更小。**

计量应从阶段 A 开始，但大范围输入优化放在正确性和流程边界稳定之后。

重点区分初次启动、正常续接、compaction 恢复、review、Planner 和返工调用。观察实际注入、必读 payload、可选展开、重复读取和宿主 usage。**字节数、token、缓存输入和实际费用分别统计，不能混为一谈。**

具体优化按收益排序：

**先减少无必要的启动和返工。** 避免本可续接却重建 Owner、重复派发、没有失败依据的重试，以及 Control 改写任务导致的重新工作。

**再去掉高频重复输入。** 检查启动提示、角色契约、packet boundary 与原生说明之间的重复职责。删除重复解释，但保留关键边界和不确定性恢复规则。每次必读的内容可以生成有界视图，可选证据继续精确定位、按需展开。

**然后细化 continuation delta。** 对高频大字段，逐步由顶层整字段替换改为有稳定来源身份的对象级变化视图。身份由脚本生成，不给 worker 增加事务字段。合并与定位也由脚本完成，不让 worker 手工应用十轮补丁链。

发生 compaction 或基线不确定时，仍然允许恢复当前完整权威视图。**不能为了避免重读，让 worker 凭不可靠记忆继续。**

R1/R2 可以共享确定性文件清单、diff 和证据索引，但不把 Owner 摘要当成审查证据，也不取消 fresh review。Aux 仅在总成本确实有收益时使用，其成本必须包含 Owner 阅读和验证 Aux 输出的部分。

重复解析、索引和锁优化按实际 profile 推进，不以减少 I/O 为由删掉可变 workspace 的必要校验。

**验收条件：** 同一任务集合、相同交付范围和验收标准下，worker 成本或有明确口径的读取指标下降，质量与强制审查不回退。基线建立之前，不设未经证据支持的节省百分比。

## 六、如何验证改造确实有效

主指标建议采用：

> **固定任务集的 worker 总成本，加上有效验收完成率。**

总成本必须包括失败、重试、评审、修复和最终未验收的尝试。每个成功 WP 的平均成本可以作为辅助指标，但前提是 WP 划分和交付范围一致，避免通过改变分母制造“降本”。


| 维度         | 重点观察                       |
| ---------- | -------------------------- |
| Control 负担 | 真正语义决策点数；仍需模型解释的确定性转移数     |
| Worker 成本  | 全部尝试的费用；初次启动与续接比例；无依据重派和重启 |
| 输入效率       | 可观测的非缓存/缓存输入、输出、必读与重复读取    |
| 正确性        | 错误验收、漏导入、漏释放、过期动作生效、必要审查遗漏 |
| 可恢复性       | 故障后是否重复启动、丢失处理进度或要求模型猜测恢复  |
| 最终质量       | 实际产物是否满足原验收条件，而不只是流程返回成功   |


上线顺序应是：离线故障测试和无副作用预演，再按 run 或 milestone 小范围启用。预演结果与既有规范或标注预期比较，**不能把历史 Control 的选择直接当作唯一正确答案**。

保留显式命令用于调试和恢复，但它们必须与自动推进共用规则和事务实现。回滚也不能靠重置 `.task`、释放全部 session 或重新派发来完成。

## 七、下一版建议收敛到的最小范围

**下一版先完成：两个事务缺陷修复、最小 dispatch 归因、统一状态/决策接口、正常候选到验收的自动推进，以及关键步骤恢复。**

对象级 delta、大范围提示词去重、索引和锁优化，在可计量、可回归之后继续推进；不要让它们阻塞正确性改造。

最终分工应当非常清楚：

> **脚本完成“已经确定该怎么做”的工作；Control 处理“理解任务后才能选择”的问题；worker 把昂贵上下文用于领域执行和独立判断，而不是维护编排协议。**
