# MATS v17.4 Review 总结与 Improvement Plan

基线：multi-agent-task-split-v17.4.rar。本文是下一版的设计与实施计划，不是已落地的修复说明。

## 1. 最终结论

将已有确定性流程组织成可恢复的自动推进链。Control 保留任务理解、歧义消解和授权范围内的语义选择，不再承担状态机解释、事务字段搬运及原生生命周期猜测。优化 I/O 的重点是昂贵 worker，而不是廉价 Control 的 token 或调用次数。

目标不是减少所有 agent 调用，而是在任务集合、交付范围和验收标准一致的前提下，减少无必要的 worker 调用、重复输入、重读和编排诱发的返工。Control 可以为了正确性增加小型状态查询；其交互总量仍应有界。

### 本次已经确定的设计取舍

| 议题 | 结论 |
|---|---|
| 正常事务推进 | 尽可能由脚本自动完成，直到需要语义选择或无法机械恢复的停止点 |
| Control 成本 | 次要指标；优先降低其流程推断负担，以及误判对 worker 成本的放大 |
| Worker 协议 | 保留稳定的角色卡、语义 TSV、脚本 finalizer、同 Owner 续接和独立评审 |
| 权限边界 | 在 skill + 原生 Codex session + Orca 的约束下，主要做防误操作；不宣称硬隔离 |
| 原生生命周期 | Orca 继续作为原生 task/session/liveness 的权威来源；不重建一套终端管理器 |
| 语义状态 | 继续保留单一 canonical 语义状态；操作日志不得变成第二份业务真相 |
| 成本优化 | 优先减少误派和重启，再处理 worker 实际上下文与读取；不以减少必要审查换成本 |

## 3. 自动化与语义决策的边界

判断标准：下一步能否仅由已验证状态、现有策略和来源记录推出？有条件分支不等于需要模型。

| 情况 | 处理方式 |
|---|---|
| 完成事件导入、去重、确认和已满足条件的清理 | 脚本 |
| R0 后派发 R1，按既定条件要求 R2 | 脚本；不让 Control 再次自由决定是否值得审查 |
| 明确的 `fix_local`，目标 Owner 与来源 finding 已确定 | 脚本续接原 Owner，保留来源原文 |
| 来源已经明确要求 commitment 变更或 `plan_conflict` | 按现有规则机械转给 Planner；无需 Control 再做一次重复分类 |
| 正常等待、可验证的同 session 恢复、明确失败后的允许重试 | 脚本 |
| 原生调用结果不明、规则冲突、状态不变量破坏 | 先机械核对；不能确认则 BLOCKED，不让 Control 猜测修复 |
| 用户新指令对应哪个任务/工作包不明确 | Control 理解任务并选择，必要时询问用户 |
| 多个合法推进方案之间涉及范围、优先级或用户偏好取舍 | Control 在既有授权内选择 |
| 需要领域证据判断才能决定局部修复还是结构性变更 | 交给有该职责的 Owner/Reviewer/Planner，Control 负责组织问题与路由 |
| 新的外部副作用或超出既有授权的承诺 | 请求用户授权；Control 不能自行批准 |

Control 不代替 Owner 解题、Reviewer 判定产品真伪、Planner 编写承诺变更，也不把源材料加工成新的设计指令。来源指令、finding 与 conflict memo 原文或其精确引用应被保留。

## 4. 目标接口与执行方式

沿用并扩展现有 `next_operation`，在现有 CLI/Guard/launcher 上构建一层薄的确定性推进器。不要同时保留一套自动内核和另一套独立手工路由实现。

以下仅为建议接口，当前版本尚未实现：

```text
mats advance
mats decide --decision-id <id> --choice <choice_id>
```

`advance` 在既定策略、现有授权和调用上限内推进，返回以下一种状态：

| 状态 | 含义 |
|---|---|
| READY | 仍有确定性工作；本次因步数/调用上限让出执行，可继续调用 |
| WAIT | 已有 worker 在运行或正在等待可验证的原生事件 |
| NEEDS_DECISION | 确实需要任务理解或授权范围内的语义选择 |
| BLOCKED | 无法验证原生结果、工具异常或协议不变量破坏；不能当成自由选择题 |
| DONE | 当前已授权范围内的工作完成并通过既定验收 |

单次 `advance` 不是跨全部原生调用的原子事务，而是多个可恢复步骤的有界组合。无需常驻服务或新平台。正常 review/repair 循环还应有独立的重复次数与新 dispatch 上限，防止自动化放大昂贵重试。

### 决策请求

```yaml
status: NEEDS_DECISION
decision_id: d42
case: DIRECTIVE_SCOPE_AMBIGUITY
question: 新指令属于现有 WP3 的范围，还是需要提交承诺变更？
source_refs:
  - user_directive_17
  - wp3_current_contract
allowed_choices:
  - id: CONTINUE_EXISTING_SCOPE
    meaning: 在既有契约与授权内续接当前 Owner。
  - id: REQUEST_PLAN_CHANGE
    meaning: 将原始指令与冲突定位提交给 Planner。
  - id: ASK_USER
    meaning: 将尚未解决的范围歧义交给用户。
```

这里的选项只是示例，实际选项必须由当前状态和既有权限筛选；不能为了凑齐选项暴露非法动作。正常情况下，确切的 plan conflict 或已明确的 in-scope continuation 不应生成这个决策请求。

Control 只返回 `decision_id`、`choice_id` 和确有必要的简短理由/来源引用。不要求它重写 packet、hash、session ID、candidate version 或整段下游指令。

脚本在执行前重新验证相关 WP、candidate、contract、授权和来源版本。依赖版本由脚本保存，不仅绑定 `plan_version`，也不宜仅因无关 WP 更新就使所有决策失效。过期决策返回新视图；不得套用到新的目标。重复提交同一决策返回既有处理结果，不重复启动 worker。

## 5. 分阶段 Improvement Plan

### 阶段 A：修复事务缺陷，并补最小成本归因（P0）

**A1 — 拒绝操作无破坏性变更。**

在任何覆盖交付草稿之前完成适用的验证与操作预留。保留既有 attempt 的交付内容；必要时将新 attempt 的草稿与旧 attempt 分离。不能只挪动一行写文件代码而忽略验证与实际调用之间的状态变化。

被拒绝操作允许追加拒绝审计，但不得覆盖既有业务产物、已有交付或权威语义状态。合法操作进入执行阶段之后留下的 intent/恢复记录，与“拒绝操作不应破坏原内容”是两个不同边界。

**A2 — 按 dispatch 维护完成与释放进度。**

逐 dispatch 持久化 `imported / release_required / released`。整批所有必要导入、one-shot release 和其他事件处理完成之后，才允许 acknowledge 与清理。Owner 不进入 one-shot 清理；事件重放时依靠持久化处理记录，而不是 tmp 文件是否还存在。

对于 acknowledge/release 返回结果不明的情况，按原生接口可提供的身份和结果核对，不假定“没有成功回执”就可以无条件重发。

**A3 — 最小归因字段。**

由脚本记录每次 worker dispatch 的 `run_id`、`wp_id`、角色、来源事件/请求、`reason_code`、启动/续接/恢复模式、对应 operation、是否由返工触发。费用与 token 从宿主确实暴露的使用量关联；未暴露则标记未知。

不让 worker 新增监控报告，也不让 Control 读取原始 session/终端历史来计算成本。

**验收：** F01/F02 两个回归测试通过；拒绝路径原草稿字节不变；多 reviewer、Owner+reviewer 混合批次、释放失败与 ack 失败不丢状态；同一完成事件重放不重复导入或触发新 worker。

### 阶段 B：把确定性“下一步”变成统一接口（P1）

**B1 — 复用已有路由，不重做领域角色体系。**

以 `routing.py` 中的现有规则、Guard 条件与原有 workflow 为基线，把确定性流程选择集中为共享代码。Guard 准入检查和下一步生成共用规则来源，避免 Markdown、Guard 与推进器分别解释同一协议。

只把可确定判断的部分下沉到代码；真正语义选择保留决策规范与案例测试。不必为了形式统一先建立一个新的通用 DSL。

**B2 — 稳定状态码和决策对象。**

以稳定 `reason_code`、结构化状态、`action_id/decision_id` 替代精确错误原文路由。错误文本保留给人阅读，不再承担机器接口契约。action 与 decision 中的机械参数均由脚本解析。

**B3 — 对昂贵调用绑定来源和适用条件。**

Planner、R2、新 Owner、重试、释放都必须能追溯到来源记录和既有规则。明确符合条件的动作自动执行；没有依据不能靠 Control 补一句解释变成合法调用。保留所有既有强制审查与 unknown 升级规则。

**验收：** 正常确定性路径不再需要 Control 解读错误字符串或重组交易参数；过期/重复 action 与 decision 不产生新副作用；真正语义歧义得到足够但有界的决策视图；工具故障不能伪装成需要模型选择的业务分支。

### 阶段 C：自动推进与故障恢复（P1，依赖 A/B）

**C1 — 有界推进正常链路。**

复用现有实现完成：事件处理 → 结果导入 → R0 → R1/必要 R2 → 明确局部修复回到同 Owner → 验收检查 → 仅当 Guard 证明释放该 Owner 是剩余阻塞项时释放 → 再次 guarded accept → 解锁下游。

多个互不冲突的就绪 WP 按既有调度策略与原生容量推进；不要仅因存在多个可执行任务就要求 Control 临场选择。仍存在实际业务优先级歧义时才停在决策点。

**C2 — 持久化逻辑操作与原生结果核对。**

为有副作用的逻辑操作保存由脚本生成的 `operation_id` 和步骤状态。可使用如下示意状态，实际字段以适配现有实现为准：

```text
PREPARED → NATIVE_PENDING / UNKNOWN → NATIVE_CONFIRMED
         → SEMANTIC_COMMITTED → ACKED → CLEANED
```

不同操作可省略不适用的阶段。只有确定没有发生的动作才可以重新执行；已完成步骤返回既有结果。外部调用结果不明时，先通过可验证的原生身份核对。原生接口无法提供安全确认/幂等能力时停止，不能承诺跨本地状态与原生调用的 exactly-once。

操作日志只记 intent、相关对象版本和回执引用，不复制整个 canonical 语义状态，也不替代 Orca 的存活真相。

**C3 — 并发和循环边界。**

在缩短原生调用周围的临界区之前，先建立锁内验证与预留、锁外执行、锁内复核提交，以及过期操作不能覆盖新状态的版本校验。使用每次推进步数、新 dispatch 次数和无进展/重复修复检测约束自动化；这些是正常入口的控制，不是无沙箱环境中的硬预算隔离。

**验收：** 在 create/start、binding 提交、import、release、ack、cleanup 前后注入故障，重启后可恢复或有据可查地停止；没有盲重试、提前释放 Owner、跳过 R2 或重复生效。纯事务恢复不要求 Control 临时设计操作。

### 阶段 D：按测量结果优化 worker I/O（P2；最小计量从 A 开始）

**D1 — 计量真实工作集。**

区分初次启动、同 Owner 正常续接、compaction/不确定性恢复、review、Planner 和修复任务。记录可观测的完整启动注入、packet、必读 payload、可选展开、重复读取、输出与宿主 usage。区分为恢复正确性必需的重读和无必要重读。

文件字节数是代理指标，不是 token、费用或缓存命中的证明。宿主未暴露的项保持未知，不按静态文件大小推算成“实际节省”。

**D2 — 高收益输入去重。**

先处理基线显示的高频重复规则和机械定位成本。将启动提示、角色契约、packet boundary 与原生生命周期说明中的重复职责整理清楚；删除重复解释时保留关键权限、来源数据不等于指令、交付和不确定性恢复边界。

对于每次必读的材料，脚本可生成一个有界的必读视图；可选证据保留精确定位与按需展开。外置材料只有不再被无必要读取时才形成收益。

**D3 — 更细且可恢复的 continuation。**

将高频大字段由顶层整字段替换逐步改成带稳定来源身份的对象级变化视图。身份由脚本生成，不给 worker 增加 ID/事务字段。不能靠相似度或 Control 摘要擅自合并两个 finding。

脚本负责合并、定位和生成可直接执行的本轮任务视图；worker 不应手工应用长期 JSON Patch 链。保留当前有效约束、原文新指令、未解决 finding、新证据定位和交付入口；基线不确定时提供当前完整权威视图。

**D4 — 保留质量保障。**

继续同 Owner 修复；不因上下文大就由 Control 自行新建 Owner。R1/R2 可复用确定性文件清单、diff 和证据索引，但不把 Owner 的摘要视为独立证据，也不取消 fresh review。Aux 不默认增加，其收益要包含高价 Owner 阅读和验证 Aux 结果的成本。

**D5 — 脚本性能。**

先修复显然的重复 YAML 解析，再按 profile 决定事务内缓存、可重建索引或锁优化。不要为省 I/O 跳过对可变 workspace 的候选/证据校验。

**验收：** 固定任务集和验收标准下，worker 实际成本或有明确口径的输入/读取代理指标下降，任务质量和强制审查不回退；报告样本量、失败与恢复成本。基线之前不承诺节省比例。

## 6. 测试与 rollout

测试矩阵至少覆盖：重复/乱序事件，多 one-shot 与混合 batch，release/ack 失败及结果不明，startup 成功但 binding 未提交，旧 candidate 回传，过期 decision，等待期间相关/无关 WP 变化，同 Owner compaction 恢复，证据变化，连续 local repair 无进展。

先在离线 fixture 和历史事件上运行无副作用的路径预演，将选择与既有规范/人工标注预期比较。历史 Control 行为不是唯一真值；新 `advance` 的 dry-run 必须真正无副作用，不能只是假设现有 `--dry-run` 不写文件。

随后按 run 或 milestone 控制启用范围。保留显式命令作为调试和恢复入口，但共用同一规则与事务实现。跨版本在途状态必须明确兼容；无法兼容就有界停止，不通过重置 `.task`、批量释放 session 或重新派发来伪装回滚成功。

### 发布门槛

| 维度 | 必须满足 |
|---|---|
| 一致性 | F01/F02 和新增故障恢复用例通过；没有漏导入、错误确认、提前释放或过期动作生效 |
| Control 负担 | 固定流程由脚本决定；Control 仅处理真实语义决策及异常报告，不解释错误原文 |
| Worker 成本 | 相同任务范围与验收口径下，统计所有尝试后的 worker 总成本，不只统计成功路径 |
| 质量 | 强制 R1/R2 条件不减少；最终产物和证据检查通过；成功率与返工原因单独报告 |
| 可恢复性 | 可确认的动作复用回执；无法确认的原生结果不盲目重发 |
| 可诊断性 | 每次昂贵调用都有来源与原因码；未知 usage 明确标注 |

推荐主指标：固定任务集的 worker 总费用和有效验收完成率，并辅助报告每个成功工作包的费用。后一指标仅在 WP 划分和交付范围一致时比较，避免通过拆分工作包改变分母。

费用包括失败、重试、必要审查、修复和未最终验收的尝试。辅助指标为 Control 的真实决策点数、误派/无依据重启数、worker 初次启动与续接比例、非缓存/缓存输入与输出（若可取得）、重复读取、P50/P95 完成时延。

## 7. 推荐的下一版最小范围

下一版优先完成 A+B+C 的最小闭环：两个缺陷修复、最小 dispatch 归因、稳定状态与决策接口、正常候选到验收自动推进，以及关键步骤恢复。不必等待完整 worker profiling 才开始修正确性问题。

对象级 delta、大范围提示词去重、索引和锁优化在可测量且可回归后推进。不是下一版前置条件的项目包括：沙箱/权限 broker、重写 Orca、更换 Control 模型、通用工作流平台、worker 交付 schema 重写，以及取消独立评审。

最终分工：脚本自动完成“已确定该怎么做”的工作；Control 处理“需要理解任务才能选”的问题；worker 的昂贵上下文用于领域执行和独立判断，而不是维护编排协议。
